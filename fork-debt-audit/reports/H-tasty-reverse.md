# H-tasty-reverse: Scala 3 TASTy format/reader -> Scala 2.13 TASTy reader

Direction reversed: ORIGIN = scala3 (`tasty/src/dotty/tools/tasty/*`, `compiler/.../core/tasty/*`), COPY = scala/scala 2.13.x (`src/compiler/scala/tools/tasty/*`, `src/compiler/scala/tools/nsc/tasty/**`).
Baseline for "what Scala 2 is supposed to read": Scala 3.7.4 (TASTy 28.7), per `project/TastySupport.scala` (`supportedTASTyRelease = "3.7.4"`) and commit 34c9fb97e9 (2026-08-18, "3.7 is the final supported version", scala/bug#13152).

Headline: the shared format layer is byte-for-byte in sync with Scala 3.7.x. No tag, section name or attribute tag supported by 3.7 is unknown to Scala 2. The only real drift is (a) the deliberate 28.7 freeze, (b) Scala 3's April 2026 reader hardening (ecfa019360) which Scala 2 lacks, and (c) cosmetic things. One incidental Scala 3 bug (outside the area) was found on the way: F4.

## Findings

### F1: Scala 2.13 rejects all TASTy >= 28.8 (Scala 3.8, 3.9, ...) although the format delta is two tags
- severity: medium (policy, not drift; "rejects valid current TASTy" but deliberately)
- confidence: high
- s3: tasty/src/dotty/tools/tasty/TastyFormat.scala:211-212 (`SUBMATCH = 48`, `INTO = 49`), :329 (`MinorVersion = 11`)
- s2: src/compiler/scala/tools/tasty/TastyFormat.scala:41 (`MinorVersion = 7`), src/compiler/scala/tools/nsc/tasty/TastyUnpickler.scala:88-100; decision commit: 34c9fb97e9 2026-08-18 "TASTy reader: 3.7 is the final supported version" (scala/bug#13152)
- what: From 3.8.0 (28.8) through 3.9.0 (28.9) the format changed only by `SUBMATCH` (a flag on MATCH, term-level; Scala 2 treats every MATCH as `unsupportedTermTreeError` anyway) and `INTO` (new modifier tag, would need to be added to `isModifierTag`, `TastyFormat.modifierTagToString`/`FlagOps` and ignored/mapped). Scala 2's `isVersionCompatible` rule (`fileMinor < toolMinor && fileExperimental == 0`) means any 3.8+ library is rejected with "Forward incompatible TASTy file" and, since 34c9fb97e9, an explicit "only supports Scala 3 versions up to 3.7" message. Libraries published for 3.8/3.9 therefore cannot be consumed from Scala 2.13 via `-Ytasty-reader`, even where the only difference is those two tags. This is an intentional project decision; listed so the audit shows the exact gap (what would have to be bumped to extend support).
- verified: `diff -w` of `object TastyFormat` bodies 3.7.4 vs 3.8.0 vs 3.9.0 vs Scala 2 (`origin/2.13.x`); grep of SUBMATCH/INTO in all of `src/compiler/scala/tools/{tasty,nsc/tasty}` (no hits; `sim` of the other 164 tag/attr constants: all referenced).

### F2: Scala 2 TASTy reader lacks the Nat/Int overflow and "section end goes backwards" hardening (infinite loop on corrupt TASTy)
- severity: low (only malformed/malicious `.tasty`; compiler hang instead of an `UnpickleException`)
- confidence: medium-high (logic reproduced, not the real private class)
- s3: tasty/src/dotty/tools/tasty/TastyReader.scala (`readNat`, `readInt`, `readLongNat`, `readLongInt` overflow checks) ; origin commit ecfa019360 2026-04-17 "Fix infinite loop with bad section ends in TastyHeaderUnpickler (#25676)"; also TastyBuffer.scala (writeNat/writeLongNat reject negatives), TreeUnpickler.scala skipTree/scanTree `firstNatTreeTag` branch `readNat()` -> `readLongInt()`.
- s2: src/compiler/scala/tools/tasty/TastyReader.scala (`readNat = readLongNat().toInt`, `readInt = readLongInt().toInt`, `readEnd = addr(readNat() + bp)`), src/compiler/scala/tools/nsc/tasty/TastyUnpickler.scala `readSection` (the `while (!isAtEnd) { ...; goto(secEnd) ... }` loop); TreeUnpickler.scala `skipTree`/`scanTree` still `readNat()` for category-2 tags (harmless without the checks).
- what: Scala 3 now rejects Nats that do not fit 31 bits, Ints that do not fit 32 bits, and varints longer than 9/10 bytes, because a length such as 0xFFFFFFFA decodes via `.toInt` to -6 and `goto(readEnd())` then moves the reader backwards. Scala 2 still does `toInt` unchecked. In `readSection` that means a section whose length decodes negative sends the cursor back to its own header and the loop never terminates unless the section name matches the requested one. I reproduced the loop with the real `scala.tools.tasty.TastyReader` from scala-compiler 2.13.18 on a hand-built file (valid header 28.7, one name table entry "Foo", one section with nameRef=0 and Nat 0x0F 0x7F 0x7F 0x7F 0xFA): the cursor loop mimicking `readSection` ran 1,000,000 iterations with `isAtEnd == false` (script: <scratchpad>/work/H-tasty-reverse/t1/T.scala). Related: the tooling-version string length in the header is also unchecked (`new String(bytes, start.index, length)` throws `StringIndexOutOfBoundsException` instead of `UnpickleException`); Scala 3 has the identical code there, so that part is shared, not drift.
- verified: read Scala 3 diff of ecfa019360; confirmed none of its checks exist in `origin/2.13.x` TastyReader (no `Expected a 31-bit nat`); no Scala 2 commit touches this since 2024-01.

### F3: Scala 2 header version check was a no-op for 2.13.13 .. 2.13.18 (reads any TASTy version) -- Scala-2-only bug, fixed on 2.13.x, not yet in a release
- severity: medium (already fixed; matters for deciding what released compilers do with 3.8+ TASTy)
- confidence: high
- s3: n/a (Scala 3 `TastyHeaderUnpickler.checkValidVersion` has no override mechanism; it always enforces `isVersionCompatible`)
- s2: src/compiler/scala/tools/tasty/TastyHeaderUnpickler.scala:109; introduced by d3e7895798 2024-01-22 (`val validOverride = possibles.isEmpty || possibles.exists {...}` with `toolOverrides` always empty); fixed by 34c9fb97e9 2026-08-18. Tags: v2.13.18 predates the fix; `git tag --contains 34c9fb97e9` shows only archive/backup tags.
- what: The Scala 2 port added `toolOverrides` (extra versions the reader may pretend to be, for RC testing). With an empty list `possibles.isEmpty` was true, so `validVersion || validOverride` was always true and the minor-version gate never fired. Released 2.13.13-2.13.18 will try to unpickle 28.8/28.9 files: an `INTO` modifier hits `readModifiers`' `assert(false, "illegal modifier tag")` (or is swallowed as a bogus rhs by `nothingButMods`/`skipTree` in `createMemberSymbol` since `isModifierTag(49)` is false in the Scala 2 table), instead of a clean "forward incompatible" message. Listed because it is the reader-side consequence of F1 for deployed compilers; no Scala 3 action.
- verified: `git log -S'possibles.isEmpty ||'`; compiled a header-only check against scala-compiler 2.13.18: `new TastyHeaderUnpickler(scala2CompilerConfig, reader).readHeader()` accepted a 28.7-exp-0 header (and the code path has no minor bound).

### F4 (incidental, outside area, scala3 bug): `handleUnpicklingExceptions` in `TastyLoader` is disabled by a leftover `if false`
- severity: high (for scala3, user-visible: TASTy load failures lose their wrapping / diagnostics)
- confidence: high
- s3: compiler/src/dotty/tools/dotc/core/SymbolLoaders.scala:537, `catch case e: RuntimeException if false =>`; introduced by ff88d25f2b 2026-10-07 "Stop checking tasty UUIDs in class files (#27205)"; present on upstream/main.
- s2: n/a
- what: The commit that removed the UUID check also edited the catch guard to `if false`, so no `UnpickleException`/RuntimeException from `DottyUnpickler`/`TreeUnpickler` is converted to the `IOException("TASTy file X could not be read, failing with: ...")` that `SymbolLoader.complete` turns into a normal "error while loading" diagnostic. It also leaves the `Option(e.getMessage)` branch dead. Looks like a debugging remnant. Relevant to this area because the "TASTy version too old/new" message path (`TastyHeaderUnpickler.checkValidVersion` -> `UnpickleException`) is what users see on forward-incompatible libraries; with the guard off it surfaces as a raw exception from the loader.
- verified: `git show ff88d25f2b -- compiler/src/dotty/tools/dotc/core/SymbolLoaders.scala`; `git show upstream/main:compiler/src/dotty/tools/dotc/core/SymbolLoaders.scala | grep RuntimeException` -> line 537 same.

### F5: Scala 2 attribute section reader `assert(false, "unknown attribute tag")` and `TastyReader.readUtf8` absent (hygiene)
- severity: low
- confidence: medium
- s3: dotc/core/tasty/AttributeUnpickler.scala (same assert), tasty/TastyReader.scala `readUtf8` (486af2f58c 2023-11-27)
- s2: src/compiler/scala/tools/tasty/AttributeUnpickler.scala
- what: Any attribute tag not in `isBooleanAttrTag`/`isStringAttrTag` (none in 28.7; Scala 3 would add a new category via a version bump) crashes the whole class load with an AssertionError rather than skipping; this mirrors Scala 3's own policy (it asserts too) and is protected by the version gate once F3's fix ships. Not a divergence, noted so nobody "fixes" it one-sidedly.
- verified: grep of attribute tags in Scala 3 HEAD vs Scala 2: constants identical (SAFEMODE was added and dropped again in Scala 3 within 28.10-exp: 3304f85ea1 / 5ee83e83a2).

## Already ported / not applicable
- TastyFormat constants (names and numeric values of every tag, section names `ASTs/Positions/Comments/Attributes`, name tags, attribute tags, `isBooleanAttrTag/isStringAttrTag`, `numRefs`, `isModifierTag`, `isTypeTreeTag`, `astTagToString`, `isVersionCompatible`, category bounds `firstNat*/firstLength*`): identical to 3.7.0..3.7.4 (diff -w clean).
- Unknown-tag behaviour for tags the Scala 2 TastyFormat lacks (SUBMATCH, INTO): unreachable on a correct build (rejected at header, F1); on 2.13.13-18 see F3. Within known tags: unsupported term trees throw `unsupportedTermTreeError` (clean error), quotes/splices/holes `abortWith` (clean), `FLEXIBLEtype` unwrapped, `ELIDED` (Java outline rhs) and any unreferenced tags are skipped generically by `skipTree` via tag category (category rules `firstNatTreeTag..firstLengthTreeTag` same as Scala 3). Hard failures remain only as `MatchError` in `readLengthType`/`readConstant`/`readVariances` for tags that cannot occur in a type position (`BIND` type, `EXPLICITtpt`, `HOLE`), and the `assert(false, "illegal modifier tag")` in `readModifiers`.
- Header/version rules: `TastyFormat.isVersionCompatible` identical; `Compatibility.failReason` identical; `TastyVersion.isExperimental/minStable/nextStable/kind/validRange` identical; major<=27 legacy branch identical; experimental-in-same-minor ("recompile with nightly") messaging identical.
- UUID: Scala 2 reads and discards it; Scala 3 stopped comparing the classfile `TASTY` attribute UUID to the `.tasty` UUID (ff88d25f2b). No parity issue. `TASTY` attribute payload (16-byte UUID, `CodeGen.scala:199`) is never interpreted by Scala 2; Scala 2 only checks for its presence (ClassfileParser `case tpnme.TASTYATTR => MissingRequirementError.notFound`, matching Scala 3's "It should have been loaded from `.tasty` file" error).
- `.tasty` sibling lookup: Scala 2 `FileUtils.classNameToTasty` (standalone-object `$.class` heuristic, excludes `Null$`, `Nothing$`, `$`) vs Scala 3 `FileUtils.classNameToTasty` (suffix `$` with the same three exclusions): equivalent for `Foo$package$.class`, `Foo$.class`, `Foo$Bar$.class`; hiding of `.class` when `.tasty` sibling exists is implemented in all three Scala 2 classpath flavours (Directory, ZipAndJar, VirtualDirectory).
- Name table: UTF8, QUALIFIED/EXPANDED/EXPANDPREFIX, UNIQUE, DEFAULTGETTER, SIGNED/TARGETSIGNED, OBJECTCLASS, BODYRETAINER, INLINEACCESSOR/SUPERACCESSOR all handled; `ParamSig` negative/positive convention the same.
- Scala 3 changes 3.4..3.7 that altered pickling without a tag change (#19951 Java annotation model, 4894414218 refined class parents, ac76938c1e annotated types, c1c1e957c5 Invisible semantics, 56b60acbc9/1f839bb2ba skolem prefixes): correspond to the Scala 2 commits 19ea949794, 0cc7d73e1e/8cb3eff978/c00adb8790 (Jan-Feb 2024), adf11521be (3.5.0-RC3), 7b4e0801e6 (3.6) and are covered by `test/tasty` against 3.7.4. Not re-verified at runtime. One residual: Scala 2 `rejectSymbol` drops any `Invisible` member outright (TreeUnpickler.scala ~551) whereas since c1c1e957c5 Scala 3 can resolve such members from `SELECTin` in TASTy trees; Scala 2 never resolves trees so no effect expected for signatures.
- Positions/Comments sections, TastyBuffer, TastyHash, besteffort/*: not consumed by Scala 2.
- Scala 3 `PositionPickler` writing line size `-1` as Nat (fixed in reader by ecfa019360): no effect on Scala 2 (never reads Positions).

## Method notes
- Port direction reversed; Scala 2's `tasty/*` files are copies with `private[this]`, `scala.tools.tasty` package and Scala 2.13 syntax, `TreeUnpickler` is a separate implementation (bridge pattern) so only the structural helpers were comparable line by line.
- Because Scala 2's baseline is frozen at 3.7.4 on purpose, "later Scala 3 commits" were split into: pre-3.7.4 (could have been missed; compared via `git show 3.7.4:<path>`) and post-3.7.4 (policy; only hardening commits considered, i.e. ecfa019360).
- Compared by `diff -w` of: TastyFormat (3.7.4/3.8.0/3.9.0/HEAD vs Scala 2), TastyHeaderUnpickler, TastyReader, TastyVersion, UnpickleException, TastyUnpickler name reader, AttributeUnpickler. All raw material in <scratchpad>/work/H-tasty-reverse/ (s2_TastyFormat.scala, s3_TastyFormat.scala, s3_374_*.scala, tags.txt, t1/T.scala).
- Not done: running tastytest against 3.7.4 (no Scala 2 build here); the F2 repro uses the 2.13.18 jar's `TastyReader`/`TastyHeaderUnpickler` (unchanged in these respects on origin/2.13.x) with a loop copied from `TastyUnpickler.readSection`, not the private `TastyUnpickler` class itself.
